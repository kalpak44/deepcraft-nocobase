# deepcraft-nocobase

Ansible + GitHub Actions that deploy onto `nocobase-lxc`, an LXC container in a
Proxmox homelab. The container is provisioned and hardened by
[`homelab-infra`](https://github.com/kalpak44/homelab-infra); this repo only
deploys onto it.

## The box

| | |
|---|---|
| Address | `192.168.1.5` (LAN only — no WAN port is open) |
| SSH | port **22022**, key-only, `PermitRootLogin prohibit-password` |
| Resources | 2 cores, 4 GB RAM, 20 GB root, 50 GB data at `/data` |
| Outbound | internet yes; the LAN is blocked except Postgres and Redis |
| Inbound | unrestricted from the LAN and from WARP |

Outbound LAN access is dropped by the Proxmox firewall on the container's veth,
so a compromise here cannot reach the rest of the network. Only two exceptions
exist, both explicit allow rules: PostgreSQL on `192.168.1.4:5432` and Redis on
`192.168.1.6:6379`.

## How CI reaches it

`192.168.1.5` is not routable from the internet. The runner joins the Zero Trust
organisation with a service token, which makes a `192.168.1.5/32` private network
route reachable through the Cloudflare tunnel:

```
GitHub runner → WARP → Cloudflare → tunnel (cloudflared @ 192.168.1.10) → 192.168.1.5:22022
```

The route is a **/32**, so an enrolled runner can reach this container and nothing
else on the LAN.

## Deploying

Pushing to `main` under `ansible/**` runs `.github/workflows/deploy.yml`, or run it
manually from the Actions tab. Locally, from the LAN:

```bash
cd ansible
export NOCOBASE_HOST=192.168.1.5 NOCOBASE_SSH_PORT=22022 NOCOBASE_SSH_USER=root
ansible-playbook playbook.yml --private-key /path/to/id_ed25519
```

The key is generated by Terraform in `homelab-infra` and lives at
`terraform/proxmox/nocobase-lxc/.ssh/id_ed25519` (gitignored). Recover it with
`just output proxmox nocobase-lxc ssh_private_key`.

## Repository secrets

| Name | Purpose |
|---|---|
| `NOCOBASE_HOST` / `NOCOBASE_SSH_PORT` / `NOCOBASE_SSH_USER` | connection details |
| `NOCOBASE_SSH_PRIVATE_KEY` | deploy key, root on the container |
| `CF_TEAM_NAME` | Zero Trust team name |
| `CF_WARP_CLIENT_ID` / `CF_WARP_CLIENT_SECRET` | service token used to enrol WARP |
| `POSTGRES_HOST` / `POSTGRES_PORT` | `192.168.1.4` / `5432` |
| `REDIS_HOST` / `REDIS_PORT` | `192.168.1.6` / `6379` |

The Postgres and Redis entries are host and port only. Credentials live in the
homelab's Vault and are not mirrored here — an app needing them has to be given
them separately.

## Accessing nginx

nginx listens on port **80** of the container.

### From the LAN

```
http://192.168.1.5/
```

Works from any device on the home network, with no DNS record involved.

### From a WARP-enrolled device

Same URL. Once the device is enrolled in the Zero Trust org, the `/32` route makes
`192.168.1.5` reachable from anywhere — this is how the CI runner does it, and it
works identically on a laptop.

Note the split-tunnel carve-out only covers `192.168.1.5`. Every other LAN address
stays on the direct path, so being enrolled does not give you the rest of the
network.

### From the public internet

**Not currently exposed.** No WAN port is open and the container has no public
hostname, so there is no URL that reaches it from outside today.

Exposing it does *not* mean opening a port. The Cloudflare tunnel already runs, so
it takes one ingress rule in `homelab-infra`:

1. In `terraform/cloudflare/shared/zero-trust/main.tf`, add the hostname to a zone
   map and give it `service = "http://192.168.1.5:80"`.
2. `just deploy cloudflare shared/zero-trust`.

Two caveats before doing that:

- The ingress `dynamic` block currently hardcodes `service = "https://192.168.1.120"`
  (Traefik) for every hostname. Pointing one hostname at a different origin means
  reworking that block to carry a per-hostname service — the map has to become
  hostname → service rather than hostname → hostname.
- `nocobase.pavel-usanli.online` **already exists** in that map and points at
  Traefik. Reusing it would take the name away from whatever serves it now, so a
  new hostname is usually what you want.

Cloudflare terminates TLS at the edge, so the container needs no certificate and no
443 listener — plain HTTP on 80 over the tunnel is the whole story. Anything
published this way is reachable by the entire internet unless you put a Cloudflare
Access policy in front of it.
